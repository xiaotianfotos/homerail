## 交付目标

输入 issue 快照、仓库/base、授权修改范围、冻结验收配置和运行预算，
一次启动 HomeRail 工作流。由一个逻辑根 DAG 推进 Codex 方案 → 修复 →
可信候选/测试 → 独立审查 → Codex Judger → 必要的反馈修复 →
创建或更新同一个 PR → 最终 head 的 CI 验收。

正常路径不需要桌面会话继续调用 plan/step/test/judge/publish。
Codex Planner/Judger 是图中的角色；本地模型可以担任 Fixer。
模型负责方案、修改和语义判断，程序负责执行事实、状态转换与发布对账。
每次模型 dispatch 用新会话和有界上下文，历史证据独立保存。
正常等待不调用模型；只在完成、异常、停滞或需要外部决策时通知。
默认产物是待合并 PR；不自动合并、关闭原 issue 或部署。

首版明确以 Linux Manager/Node、隔离工作树/测试容器和 GitHub 为执行平台。
Windows 是必须支持的远端 CI 验收目标；不把 Linux 执行器冒称原生 Windows 执行器。
任意供应商、任意 issue、任意进程状态的无损恢复不在首版保证范围。

首次真实演练的 issue 在 P0 按可复现性、验收清晰度、限定范围选择并记录；
第二个应覆盖不同修复形态（例如单文件逻辑与跨文件契约），不只重复同一提示词。

## 如何判断是真正 E2E

最终验证由独立验收脚本读取原始事件、回执和 GitHub API，不采信模型自报成功。
每个验收项输出 `passed / failed / not_run / inconclusive` 和证据路径。

1. **控制流归属**：只允许测试驱动器发出初始 start、预先声明的故障注入和只读采集。
   审计模型 dispatch、阶段推进、测试、review、提交、PR、CI 派发的调用来源。
   正常路径的外部人工推进、手改候选和手写 Judger 决策均必须为0。
   故障测试允许明确标注的故障注入；暂停后人为 resume 另列为 assisted，不能计为无人干预成功。
2. **修复正确性**：基线必须能复现缺陷；候选必须通过冻结测试及必要回归。
   至少一个试验必须先失败再通过；不能故意降低测试质量或只改报告来构造“收敛”。
3. **发布结果**：必须存在真实 PR、可信程序创建的提交和可核对的最终 head。
   提交/PR/CI/审查/测试回执必须绑定同一候选；只有本地补丁或 ready_for_ci 不算完成。
4. **上下文**：记录每次实际会话/dispatch ID、输入字节数及上下文构成。
   完整历史不直接拼接进下一轮；压缩摘要必须指向原始 artifact，遗漏信息可按需检索。
5. **恢复效果**：比较注入前后模型调用、测试执行、提交和 PR 数量。
   只重试确实丢失的阶段；不能仅凭最终成功就声称复用了 token。
6. **无干预证明**：关闭作为调用者的 CLI/桌面对话连接仍可推进。
   保留程序级事件监督；不靠后台循环不断调用外部模型来扮演隐藏调度器。

审查政策遵循本次用户澄清：**必需 CI 全绿，至少两票独立完整审查通过**。
审查异常不能当 approve；缺失/截断结果单独标记，不能伪装三份完整报告。
每条保留 finding 由 Judger 明确接受修复、凭证据驳回或升级；两个 approve
不能抹去已确认但未解决的正确性问题。误报不应导致无意义的修复或无限重跑。
政策必须在工作流启动时冻结并由程序执行，不在运行末尾临时改票凑成功。
同 head 的既有审查可按身份和策略复用；新 head 不能借用旧票获得通过。

必需 CI 的清单从仓库工作流和冻结验收配置解析，并检查实际执行 jobs：
`success` 才算通过；missing、skipped、cancelled、timed_out 均不能冒充 success。
适用环境应明确，非必需 job 不计入分母；观察失败必须保持 unknown。
当前 HomeRail 完整验收矩阵为 Linux Node20/24、Windows Node24、UI coverage、Docker smoke。
基线或 PR head 变化时重新判断证据适用性，不能只检查 workflow 总状态。

## 必须覆盖的故障与反例

| 注入点/反例 | 必须得到的结果 |
| --- | --- |
| create 已接受但响应丢失/502/504 | 依原始 execution/run ID 对账；不重复派发 coder |
| intent 写入后、执行启动前退出 | 可确定未执行才启动；不把 unknown 当未执行 |
| 执行已启动但 ack 丢失 | 接回原进程/容器/远端 run；不启动第二份 |
| Manager 在测试、CI 等待或反馈边界重启 | 恢复受支持的持久阶段；保持根任务/轮次/候选身份 |
| 模型首 token 后 Worker/Manager 退出 | 保存已落盘证据；明确标记损失，必要时新会话重新执行该模型阶段 |
| 测试被杀/OOM/依赖安装失败 | 分类为执行/环境问题；有限重试同一候选，不立即让 Fixer 改业务代码 |
| 真实断言失败或负面审查 | 带完整可引用证据回 Judger，批准下一份方案；不按基础设施重试吞掉 |
| 双恢复进程、过期 lease/owner epoch | 一个有效所有者；旧执行回调不得推进新轮次 |
| 重复/迟到通知、回执完成后篡改 | 幂等消费；篡改报警且不通过、不重执行 |
| PR 创建/更新已接受但响应丢失 | 只读对账同一个 PR/同一 head；未知状态暂停，不盲目再发 |
| CI 观察断网、workflow attempt/head 漂移 | 恢复原观察或明确证据失效；不重跑 coder 或虚报检查通过 |
| 伪造 TestReport、改哈希、删测试、修改 runner | 可信门禁拒绝；改变验收定义需要显式计划/策略边界 |
| 一再重复相同失败、无效格式改动、超预算 | 保存最佳已验证候选后暂停；不无限循环 |
| 两票通过 + 一条有效 blocker / 一条可证伪 finding | 前者修复/升级，后者留证据驳回；不简单按票忽略语义问题 |

故障矩阵须在“执行前 / 已执行未确认 / 已确认”分别覆盖，记录预期与实际
副作用次数。恢复规范只保证已声明的阶段；不以任意复活终态 run 冒充恢复。
提交后的代码、测试、审查发生变化，都要回到身份校验而不是沿用旧 accepted 状态。

## 成本、收敛与模型能力的评估

每次尝试记录：根 run、轮次、计划摘要/hash、候选 head/tree、模型/角色、
会话 ID、输入大小、输入/输出 token（未知必须保留 unknown）、耗时、
有效测试数、失败指纹、审查 findings/处置、CI jobs、重复执行次数和人工干预。
分别统计模型耗时、测试耗时、远端 CI 排队/执行、恢复耗时，不能把排队算模型性能。
若能获取首 token 和完成时间，分别报告 TTFT、生成速率；没有就不推算。

先用相同 issue 快照、基线、模型配置和验收命令建立一个一次性修复对照，
再与循环结果比较。报告成功数/总尝试数、首次通过率、最终完成率、总 token、
重复推理、总耗时和恢复后的增量成本；历史实验数据只作背景，不当作本次对照。
保留失败和预算耗尽的全部结果，不只挑成功样本。小样本不宣称统计显著或普适提升。

初始实验预算（策略配置，模型不得自行增加）：最多4轮修复，每外部阶段
最多2次可证明安全的基础设施重试；同一失败指纹连续2轮无有效进展时
要求 Codex 重新制定方案，下一次仍无进展则暂停。每节点输入先设96KiB上限，
但同时以实际模型上下文窗口/输出预留校验 token 预算，字节上限不能代替 token 上限。
运行总时限、单阶段时限和 dispatch 上限在 P0 按真实环境显式冻结。
新增 run/attempt 的重试仍计入根任务预算，重启不能清空预算计数。

“能收敛”的交付结论是：在限定问题集合内，有证据的反馈能改善候选并完成验收；
不承诺任意问题一定修好。无法修好的问题必须可靠暂停且可解释，不能变成假成功。

## P0 契约落地记录

`homerail_protocol/src/e2e-fix.ts` 定义候选身份与验收输入，供 Manager 的
可信存储适配层使用。身份包括 task/root run/round、plan/policy digest、
repo/base/head/tree。32 个定向用例覆盖当前身份、必需 CI、审查独立性、
Judger 对报告和 finding 的绑定、PR/工作流目标，以及异常/缺失证据。

`evaluateE2eFixAcceptance` 只检查已经由可信存储加载和验证过的记录，返回
是否有资格完成，不执行测试、不验证哈希对应的文件，也不提交终态。
后续 Manager 适配器必须自行读取回执/报告、校验来源和字节，禁止将模型
提交的一整份 acceptance JSON 直接传入。这个模块单独通过测试不算 P1/P2 完成。

模型 handoff 只能提出方案、候选修改或 Judger 决策。测试、发布与 CI 字段
必须来自可信适配器，policy 必须来自启动时冻结的 Manager 配置。
适配器对每个 check 先按执行意图确定唯一有效 attempt；不能从历史中挑一个
通过结果遮住后来的失败。不同 workflow/PR 即使具有相同 head 也不能替代。

## P1 原生流程验证记录

`homerail_manager/src/orchestration/e2e-fix-workflow.ts` 生成可经现有 WorkflowSpec
编译器校验的原生图。循环回边、测试结果分支、独立审查汇合、两个 Judger
位置（候选/CI）、发布与结束分支均由 DAG 调度；程序阶段的 argv 只能来自
可信宿主配置，模型节点禁用内置文件/shell工具，使用新 dispatch 会话。
目前尚未注册为可直接部署的 Asset：程序阶段仍需 P2 的候选/测试隔离与可信证据适配。

`homerail_manager/tests/e2e-fix-workflow.test.ts` 在真实 GraphExecutor 上验证：

- 初始 start 一次；模型传输替身仅响应原生 dispatch，不指定下一节点或轮次。
- 实际 Git 候选与实际 Node 断言：第一轮正数加法失败，第二轮正数通过但独立
  负数探测失败，第三轮通过；三个候选和历史 handoff 均保留，所有模型会话唯一。
- CI 场景在发布后实际执行额外类型检查，失败回到 Judger 和第四轮修正，
  发布适配器接收两次更新且 PR 身份相同。
- 两轮预算耗尽和模型错误批准真实失败测试均停止，不发布失败候选。

模型与 GitHub 服务在这些测试中是替身，GitHub CI 的检查命令在本地执行。
因此证据只证明原生控制流和节点交接，不能证明真实 GitHub 副作用、供应商
模型效果、远端文件边界、重启恢复或平台隔离。测试 helper 明确留在 fixtures
目录，不可作为生产可信执行器。验收输入中模拟的 provider身份也不能冒称真实签发。

本次验证修正了编排本身的三个错误：终止分支与仍等待反馈的循环节点做 join
会互等；默认50 handoff不足以完成该图三轮；默认边遍历3次不足以进入第四轮。
现在为每个终止分支设置直接终态，按限定轮次分别冻结模型dispatch、handoff和
边遍历预算；没有关闭边界或把循环改成外部脚本。

初版 P1 使用同步 command。以下 P2 记录说明已替换的传输，以及仍待完成的边界。

## P2 持久程序传输验证记录（尚未完整通过 P2）

原生 `command` 增加显式 `durable` 模式，E2E Fix builder 默认使用它。
这仍是一个原生图：独立 runner 只执行一次程序，不知道下一节点、修复轮次或
模型调用。Manager 写入执行 intent 和 RUNNING 状态后才启动它；执行器的
一次性 claim、会话/轮次身份、所有者 epoch 和事务内消费防止重放副作用或旧回调推进。
程序退出结果和日志由 runner 落盘；完成通知触发原生图继续，普通等待不调用模型。

新增验证分成三层：

- 独立执行器故障测试：执行前退出后的启动、丢失启动应答、重复启动、所有者替换、
  重复消费、事务失败、回执/日志/intent/runner篡改、模型伪造报告、命令身份冲突、
  真实断言失败、超时、输出溢出、启动前/执行中取消、runner丢失与事件去重。
- 原生图恢复：运行中和已完成未消费时恢复，保持原会话并只执行/交接一次；
  格式错误进失败分支，取消后的回调不能完成 DAG，动态 executable 不能进入持久模式。
- 真实进程故障：独立 Manager 运行时子进程启动测试后被 SIGKILL，测试 runner
  留存运行；新 Manager 进程读取同一根 run/会话，原测试完成后自动消费并结束。
  测试驱动仅负责预先声明的进程故障和释放原测试，不调用 handoff 或下一阶段。

原有四个多轮控制流场景也改用该异步传输，继续验证实际 Git/Node 断言、反馈
回路和预算终止。模型、发布和 CI provider 仍是替身；这些用例不是生产 E2E 证据。

**边界**：Linux 宿主可信程序传输已经落地，不等于候选测试容器已隔离，也不等于
真实 GitHub 操作具有幂等性。进程丢失且没有回执时明确 unknown，不能从哈希或
缺少应答推断“未执行”并重跑。任意同 UID 恶意宿主程序不在文件权限信任边界内。
runner 继承宿主环境，因此模型候选必须由后续可信适配器送入隔离容器执行。

后续：冻结候选和测试定义，落地阶段 adapter、证据来源验证、失败分类/有限重试，
补齐跨节点文件边界及反馈边界恢复矩阵，再进入真实模型和 GitHub 验证。

## P2 候选与隔离测试组件（尚未接入完整阶段 adapter）

`e2e-fix-candidates.ts` 使用任务私有 bare Git 库，只拉取冻结 base，不改调用方
工作树、index 或分支。精确 old/new 修改受冻结路径范围约束，禁止改受保护的
测试定义；重复、模糊、过期、无变化和越界补丁均拒绝。提交内容、作者时间和
身份可复现，同一轮重放得到同一 Git head，另一份提案不能覆盖已经捕获的轮次。
候选绑定 Git tree、base、任务、根 run、轮次和计划/政策，快照按实际 Git blob
核对，不接受仅有模型声明 head/hash 的目录。首版仅接受 UTF-8 模型编辑、常规
Git 文件，完整快照上限64MiB/10000文件；当前 HomeRail 基线约20MiB，落在范围内。

`e2e-fix-test.ts` 提供一次可信 Docker 测试操作。候选快照与冻结测试定义分别
只读挂载，测试在 tmpfs 副本中构建/执行，使用非 root 用户、无网络、无额外
capability、无 Docker socket 或 Manager 私有目录挂载。镜像由不可变 image ID
指定；可选依赖模板必须预先从可信 base 构建进该镜像。候选阶段不在线安装依赖。

Docker 创建与启动意图、实际容器 ID、输出捕获和退出状态分别持久化。丢失
create 应答时只读对账；已启动或结束的容器不再次 start。宿主程序直接附加并
有界捕获测试输出，禁用 Docker 日志轮转作为通过证据来源。输出连接丢失、
超时或OOM不能冒充断言失败或通过；未知状态需要恢复适配器进一步处置。
正常断言失败由容器和 Docker attach 的一致非零退出码确认。

真实 Docker 组件试验使用同一份冻结测试：Git 基线断言失败，修复候选通过；
测试也验证了候选和测试定义不可写、Docker socket不可见、宿主测试环境标记
未传入容器。报告保存原始输出、容器状态、Git身份与配置，并与注入 Docker
替身的故障测试分开。Linux 组件用例不冒称 Windows 宿主支持；Windows 仍须
作为远端 CI 目标验收，普通原生拓扑用例在 Windows 走已有同步夹具。

这些组件尚未替代 P1 全图中的程序阶段夹具。后续必须由可信阶段服务加载冻结
任务配置、验证真正的模型 dispatch/会话来源、接入上述组件并汇总验收输入；
再验证完整图跨阶段恢复，不能把单独两次调用测试组件当作无人干预 E2E。
进程回执证明固定程序确实执行及其结果，不是对所有潜在断言或候选语义的数学
证明；独立语义审查和 Judger 仍不可省略。

## P2 可信阶段接入原生整图（生产 E2E 仍待验收）

`e2e-fix-stage.ts` 现在为原生图提供单阶段适配器。固定 argv 指向任务私有配置；
阶段从 Manager 的持久 command、run、节点和会话记录核对实际执行身份、输入及
反馈轮次。模型 handoff 不能指定另一任务、轮次或可执行程序。Planner、Fixer、
Reviewer 和 Judger 的交接来自实际节点记录，保存会话、后端、交接摘要和有明确
会话范围的 usage 快照；缺失 usage 标为 unknown，不将累计快照当作增量相加。
生产模式要求 Planner/Judger 配置为 `codex_appserver`；真实 Worker 的执行身份
和模型预算仍需 P3 验收，配置后端不等于完成实际模型证明。

冻结配置绑定 issue、base、可写/保护路径、测试镜像/命令、审查/CI政策、最多轮次、
基础设施重试次数、输入字节与总时限。下一轮只取当前候选源码、上一轮简要反馈
和冻结任务信息；完整过程独立保留。实际 Git 候选、隔离 Docker 测试、审查汇总、
Judger 记录和最终共享门禁已接入原生 while/feedback，适配器不包含另一套修复循环。

异常分类遵循以下行为：

- 过期、模糊或越界补丁保留为 proposal_rejected，不执行候选测试；Judger 可批准
  新轮次，沿用最后可用的候选，明确提供拒绝原因。宿主 Git/证据异常不能冒充补丁错误。
- 断言失败进入 Judger；确定的隔离测试中断仅在预算内重试同一候选，原回执保留。
  仍然未知或基础设施异常暂停，不要求模型修改业务代码。
- 至少两票通过仍不能跳过 finding 处置；处置必须完整、唯一并引用已提供的证据。
  未处置、重复处置或自相矛盾的 approve 阻止发布。误报可由 Judger 留证据驳回。
- 只有当前候选、同一 PR 和冻结工作流的完整 CI job 失败可进入代码修复。
  缺失、未知、重复 job 或旧 head 的 CI 不能驱动 Fixer，也不能宣布完成。

新增整图试验仅替换模型/GitHub provider，程序阶段全部调用上述实际实现。
一次 start 后，原生图独立完成真实 Docker 断言失败 → 通过测试但收到语义审查反馈
→ 第三轮通过的流程；另测无效补丁修复、未知/旧 head CI 暂停，以及两票通过时
未处置 finding、重复处置、凭证据驳回这三种情况。每次模型 dispatch 都是新会话，
原始 Git、测试输出/回执、轮次记录、阶段命令身份和 DAG 快照单独导出。
这里的语义审查是确定性替身，GitHub 无网络调用；即使模拟门禁通过，结果仍明确
标记 `production_eligible: false`，不能算作真实模型或真实 PR 成功。

## P2 运行时快照边界

新增 `freezeE2eFixRuntime`：从已构建的 Manager 复制 `dist`、生产依赖闭包及当前
Node 二进制。依赖使用快照内部链接，保留嵌套版本，不连接原安装目录，也不执行
npm 安装脚本或下载。清单绑定每个文件的内容、可执行权限和链接目标；每次阶段
调用先用 Node 内置模块核对清单，再加载任何 Manager 或第三方代码。缺失、篡改、
多余文件和外部依赖链接均拒绝。快照上限为512MiB/20000项，保存在宿主私有目录。

可信启动方将返回的 `sha256` 写入任务 `runtime_sha256`，用
`frozenE2eFixStageCommands(runtime, taskDirectory)` 生成 argv，并把该快照的
Node 路径加入 command allowlist。生产模式要求冻结运行时；阶段将启动器验证的
摘要与任务政策再次核对。恢复时用已保存的目录和摘要调用
`loadFrozenE2eFixRuntime`，不能重新跟随当前构建生成另一版本。

验证包括：原安装目录删除后继续调用、嵌套依赖版本不混淆、清单/模块/链接篡改
拒绝、缺失必需依赖不发布半成品，以及真实编译 CLI 在原生 durable command 中
执行初始化。相同运行时摘要可执行；任务摘要不同则在创建候选 Git 前拒绝。
这些证明版本隔离和阶段身份，仍不是模型、GitHub 或整个修复任务恢复的证明。

边界：快照固定 JavaScript、npm依赖和Node，不固定宿主内核、系统动态库、Git或
Docker服务；升级这些组件后的兼容性仍需验证。该机制依赖可信宿主和私有目录，
不防御同 UID 的任意恶意宿主程序。跨数据库版本迁移也不能靠旧快照自动保证。
后续真实部署必须对已运行任务采用兼容升级策略，或先结束任务再迁移数据库。

## P2 GitHub 程序阶段（尚未通过真实发布验收）

阶段 CLI 已接入生产 GitHub provider。冻结配置增加目标 base 分支、必需 job 的
精确名称映射、checkout action 的完整提交 SHA 和观察时限/间隔。模型没有 GitHub
凭证；宿主程序通过已有 `gh` 身份调用固定 GitHub API，并使用其 Git credential
helper 推送任务专属 `codex/e2e-fix-*` 分支。启动真实任务前必须确认该身份具备
目标仓库和 Actions 权限；本实现不会给模型配置 token 或开放发布工具。

发布前核对私有候选 Git、冻结 CI workflow 内容和已发布历史的祖先关系。
分支更新带精确 lease；PR 的仓库、分支、base、任务标记、正文和编号均持久绑定。
首次创建 draft PR，后续轮次更新同一分支/PR，不另建 PR。关闭或丢失的已拥有 PR、
外部分支修改和身份不符均拒绝。创建与推送先持久化意图及一次性 claim；写请求
应答丢失时只读对账，不能因为未收到成功响应就再次创建或覆盖。

当前仓库没有 pull_request synchronize 触发，因此程序显式 dispatch CI，并冻结
candidate head 为 target_ref。记录派发前已有 run，排除它们，再绑定唯一新 run
及 attempt；等待仅由宿主阶段程序执行，不消耗模型 token。每个必需 job 精确匹配
名称与结论，重复、缺失、跳过、旧 head、attempt 漂移和观察失败不能算通过。

此外读取每个必需 job 的原始日志，核对冻结 checkout action 在第一个执行步骤
输出的实际 `git log -1 --format=%H`。仅解析 checkout 到下一步骤之前的区间，
不接受候选代码随后打印的同名命令或 SHA。取不到日志、格式不支持或 head 不符
均保持 unknown；不能以 workflow head 或提交的 target_ref 代替实际 checkout。
这依赖可信 GitHub 服务及冻结 workflow 的“checkout 是第一个 action”契约，
不是任意 CI 系统的通用证明。已用本仓库历史 Linux 和 Windows 原始 CI 日志核对
该格式；这两份历史日志只证明解析兼容性，不计入新候选的 CI 成功证据。

失败 job 的完整日志留在宿主证据目录，有界摘要随 CI 证据进入 Judger，再传给
下一轮 Planner。新增原生整图用例验证 CI 失败 → 图内修复 → 同 PR 更新 → 验收，
仍使用模拟模型和 GitHub。API 注入测试覆盖丢失 push/create/dispatch 应答、重复
调用、分支漂移、未知创建结果、重复 run、attempt 漂移、缺失/跳过 job、错误
checkout 和日志反馈。真实 GitHub 写入、真实模型及整个任务恢复仍须 P3/P4 验收；
这些测试不授权把模拟结果标为生产通过，当前也未创建实现 PR 或演练 PR。
